## What makes it 22 MB / load time
- 23 PNGs = 20.6 MB of base64 (~15 MB binary; 1.3-2.6 MB each; many are AI-generated cartoon infographics at ~1,100-1,700 px wide). This is ~90% of the file.
- Babel standalone (3.1 MB uncompressed, gz in file), React + ReactDOM *development* builds (1.2 MB), fonts 0.9 MB (20 woff2 files), app code ~0.06 MB.
- Yes, it is a real load-time problem: students must download ~22.8 MB before anything shows, then the page base64-decodes everything, decompresses and creates blob URLs, then Babel compiles the JSX in the browser. On school Wi-Fi/Chromebooks expect long blank/"Unpacking..." time (tens of seconds), and a failed/partial download gives a blank page. Not fixed (restructure out of scope). Suggested: convert PNGs to compressed WebP/JPG (probably 22 MB -> ~3 MB), switch to production React builds, and/or split images out as separate lazy-loaded files like the other topics.

## Bigger issues (not fixed; owner decision)
1. **Auto-complete by scroll position is easy to game and can fire on load.** Any section with no MCQ is ticked as soon as its top is above 55% of the viewport, so on a tall monitor several sections tick instantly without being read, and the certificate unlocks at 100% sections even if the student never answered a quiz (certificate shows e.g. "0 / 0 Questions correct"). Also a student who manually unticks such a section has it re-ticked on the next visit. Suggest: require dwell time (e.g. section visible >= N s) or require manual tick for non-quiz sections, and hide the certificate unless `answered>0`.
2. **Certificate is trivially forgeable / not verifiable**: the "verification code" is a client-side hash of name+stats only; the student typed their own name; any student can generate one by editing localStorage. Fine as a motivator, but don't treat as proof of work.
3. **Home link `href="/"`** (hub "All years", topic "⌂ All year groups") resolves to `irvincisneros-png.github.io/` (user root) since each year is a project site (`/Year-7/`). Correct only if the new site homepage is deployed at that user-root repo. If not, change to an absolute URL.
4. **Section card "Open section" link colour and a few inline-styled accent texts** in kit.jsx use `var(--accent-deep)` inline and cannot be fixed from CSS; still low contrast in dark mode for the general (#3c4655) branch. Easy follow-up: add a `--accent-text` token.
5. `.btn-accent` (white on --accent) is below 4.5:1 for orange/amber/blue accents; branch accents are mostly darker so only affects topics that set `data-accent`. Check visually.
6. quiz-feedback `role=status` is inserted together with its text so some screen readers will not announce it; low priority.
7. Export/import progress uses `indexOf(SKEY)===0` prefix matching (e.g. a future `y8.change2` would match `y8.change`); harmless today.

## In-browser Babel: performance and a safe precompile approach (report only)
- Each page downloads babel.min.js (3.1 MB; ~0.8-1 MB gzipped from GitHub Pages, cached after first visit) and then transpiles kit.jsx (57 KB) + content.jsx (80-110 KB, up to 109 KB) every load. Measured on an Apple-silicon Mac: Babel parse ~80 ms + ~350 ms of transforms for a typical topic; periodic-table and diseases ship ~285 KB of JSX each (roughly 3x that).
- On a school Chromebook (Celeron/MediaTek class, typically 5-8x slower single-thread) expect roughly 2-4 s of main-thread blocking for a normal topic and 6-10 s for periodic-table/diseases, with the "Getting your science ready..." spinner frozen (the spinner is CSS so it keeps spinning, but input is dead). First visit on a throttled school network adds the 3 MB download. YES, noticeable, and the 12 s "This page didn't finish loading" overlay can falsely fire on slow devices/networks for the two big topics. Easy mitigation: raise the 12 s timeout to ~30 s.
- Safe precompile plan (no behaviour change): (1) add `package.json` with `esbuild`; (2) a script `build.mjs` that, for each topic, transforms `shared/kit.jsx` (+ `hub.jsx` for hubs) and `content.jsx` with `esbuild --loader:.jsx=jsx --jsx=transform` (classic React.createElement, same as Babel `presets:['react']`; NO bundling, NO minify needed beyond optional) to `shared/kit.js`, `<topic>/content.js`. Because the files are global-scope scripts that rely on top-level `const {useState}=React` and `Object.assign(window,...)`, keep them as plain scripts (do not use `--bundle`/`--format=esm`); for periodic-table/diseases transform each file individually in the same order. (3) Change `<script type="text/babel" src="x.jsx">` to `<script src="x.js">` and delete the babel.min.js tag (can keep vendor file unused). (4) Commit the generated .js files (GitHub Pages has no build step) and add a `npm run build` + a pre-push check that fails if .js is older than .jsx. (5) Verify with the existing per-topic smoke test (page sets `window.__mounted`). Keep the .jsx as the source of truth. Result: page loads ~3 MB less JS, 0 transpile time, no CSP `unsafe-eval` needs. One gotcha: esbuild's JSX transform will not hoist `const` declarations differently from Babel, but any `text/babel`-only quirks (e.g. top-level `await`, `import`) are absent from these files (esbuild already parses them all cleanly).
